cmdi-001
  Template: ; whoami
  Purpose: Semicolon command separator - executes whoami after original command (Linux/Unix)
  🛡️  Defense: Input validation: whitelist allowed characters. Never pass user input directly to system(), exec(), shell_exec(). Use argument arrays, not shell strings.


cmdi-002
  Template: | whoami
  Purpose: Pipe operator - passes output of first command to whoami (usually shows username)
  🛡️  Defense: Avoid shell execution entirely. Use language-native APIs (subprocess with shell=False in Python, child_process.execFile in Node).


cmdi-003
  Template: || whoami
  Purpose: OR operator - executes whoami if first command fails
  🛡️  Defense: Principle of least privilege: run application with minimal OS permissions. Disable shell access if possible.


cmdi-004
  Template: & whoami
  Purpose: Background execution - runs whoami in background (Linux/Unix)
  🛡️  Defense: Use parameterized command execution. In PHP: escapeshellarg() + escapeshellcmd() as last resort, better to avoid shell.


cmdi-005
  Template: && whoami
  Purpose: AND operator - executes whoami only if first command succeeds
  🛡️  Defense: Strict input validation: whitelist known-good inputs. Monitor process execution for anomalies.


cmdi-006
  Template: & whoami
  Purpose: Windows command separator using ampersand
  🛡️  Defense: On Windows: use subprocess without shell=True. Avoid cmd.exe entirely. Use Windows API directly when possible.


cmdi-007
  Template: | whoami
  Purpose: Windows pipe operator - works in cmd.exe and PowerShell
  🛡️  Defense: In .NET: use Process.Start() with argument lists, never with shell command strings.


cmdi-008
  Template: 
 whoami
  Purpose: Newline separator - executes as separate command in some contexts
  🛡️  Defense: Normalize and validate input. Remove/escape control characters including newlines and carriage returns.


cmdi-101
  Template: `whoami`
  Purpose: Backtick command substitution - output of whoami replaces the expression (Linux/Unix)
  🛡️  Defense: Never use shell metacharacters in commands. Whitelist approach: define allowed values, reject everything else.


cmdi-102
  Template: $(whoami)
  Purpose: Dollar-parenthesis command substitution - modern syntax in bash/sh
  🛡️  Defense: Use application-level functions instead of OS commands when possible. For file operations: use language file APIs, not cat/ls/dir.


cmdi-103
  Template: %USERPROFILE%
  Purpose: Windows environment variable expansion - can leak sensitive paths
  🛡️  Defense: Disable or sanitize environment variable expansion. In cmd.exe, use setlocal to limit variable scope.


cmdi-104
  Template: ${IFS}
  Purpose: Internal Field Separator variable - used to bypass space filtering in bash
  🛡️  Defense: Blacklist filtering is insufficient. Use structured command execution (execve with argv array).


cmdi-201
  Template: > /tmp/output.txt
  Purpose: Output redirection - writes command output to file (potential for file creation/overwrite)
  🛡️  Defense: File system permissions: ensure web user cannot write to sensitive directories. Monitor for unexpected file creation.


cmdi-202
  Template: < /etc/passwd
  Purpose: Input redirection - reads from file and uses as command input (potential information disclosure)
  🛡️  Defense: Restrict read access to sensitive files. Use SELinux/AppArmor to enforce mandatory access control.


cmdi-203
  Template: 2>&1
  Purpose: Error redirection - combines stderr with stdout (can reveal error messages with sensitive info)
  🛡️  Defense: Don't display raw command output/errors to users. Log securely, show generic error messages to users.


cmdi-204
  Template: > C:\output.txt
  Purpose: Windows output redirection to file
  🛡️  Defense: On Windows: NTFS permissions to restrict file operations. Use User Account Control (UAC) properly.


cmdi-301
  Template: wh''oami
  Purpose: Empty string injection - bypasses simple string matching for 'whoami'
  🛡️  Defense: Don't rely on blacklisting commands. Whitelist allowed inputs or avoid shell execution entirely.


cmdi-302
  Template: who$@ami
  Purpose: Special variable insertion ($@ = empty in many contexts) to obfuscate command
  🛡️  Defense: Complex bypass attempts indicate attack. Use allowlist validation + logging of rejected inputs.


cmdi-303
  Template: w\ho\am\i
  Purpose: Backslash escaping - can bypass pattern matching in some shells
  🛡️  Defense: Normalize input before validation. Remove escape sequences or reject inputs containing them.


cmdi-304
  Template: /usr/bin/who``ami
  Purpose: Full path + empty backticks - bypasses command name filters
  🛡️  Defense: Whitelist acceptable values, don't blacklist commands. Better: don't use shell at all.


cmdi-305
  Template: ;{cat,/etc/passwd}
  Purpose: Brace expansion in bash - {cat,/etc/passwd} expands to 'cat /etc/passwd'
  🛡️  Defense: Use bash with --norc --noprofile options if shell is unavoidable. Better: use execve() directly.


cmdi-306
  Template: who^ami
  Purpose: Windows caret escape character - 'who^ami' becomes 'whoami' in cmd.exe
  🛡️  Defense: On Windows: avoid cmd.exe. Use ProcessStartInfo with UseShellExecute=false in .NET.


cmdi-307
  Template: ;ca\t${IFS}/etc/passwd
  Purpose: Combined obfuscation: backslash escape + IFS variable for space
  🛡️  Defense: Multiple obfuscation layers indicate sophisticated attack. Defense: no shell execution + strict validation.


cmdi-308
  Template: %0a whoami
  Purpose: URL-encoded newline separator - may execute as separate command after decoding
  🛡️  Defense: Decode user input, then validate. Check for encoded metacharacters. Reject, don't try to sanitize.

xss-001
  Template: <script>alert('XSS')</script>
  Purpose: Basic script tag injection - most common XSS pattern when user input is reflected in HTML body
  🛡️  Defense: Modern browsers and CSP policies block inline scripts. WAFs detect <script> tags easily.


xss-002
  Template: <img src=x onerror=alert('XSS')>
  Purpose: Event handler injection via img tag - triggers when image fails to load
  🛡️  Defense: Content Security Policy (CSP) with 'unsafe-inline' disabled prevents this. Input sanitization removes event handlers.


xss-003
  Template: <svg onload=alert('XSS')>
  Purpose: SVG-based XSS using onload event - alternative to img tag
  🛡️  Defense: Modern WAFs recognize SVG event handlers. Proper HTML sanitization libraries (DOMPurify) remove these.


xss-004
  Template: <body onload=alert('XSS')>
  Purpose: Body tag with onload event - executes when page loads
  🛡️  Defense: Rarely works as it requires injecting into or replacing body tag. Sanitization prevents this.


xss-005
  Template: <iframe src=javascript:alert('XSS')>
  Purpose: JavaScript protocol in iframe src - executes JS in iframe context
  🛡️  Defense: CSP frame-src directive blocks this. Modern browsers restrict javascript: protocol.


xss-101
  Template: " onmouseover="alert('XSS')"
  Purpose: Breaking out of attribute value to inject event handler - common when input is in href, src, or value attributes
  🛡️  Defense: Attribute encoding and strict attribute validation prevent this. Never insert user data into attributes without encoding.


xss-102
  Template: ' onclick='alert("XSS") '

xss-103

xss-104

xss-201

  🛡️  Defense: Never put user input directly in <script> tags. Use JSON encoding and proper escaping. Consider using data attributes instead.


xss-202

xss-302
